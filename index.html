从使用到价值，还需要验证

3% 是引导语点击率，11%→39% 是提问 UV 率，两者不是同一个指标。作品表现的变化也不能直接排除创作者选择差异等因素。

回看：继续观察建议采纳与后续创作，判断增长是否真正转化为用户价值。把诊断前置到选题，是下一步探索方向。

页面能跑起来，
不代表业务能跑下去。

首版测试覆盖了场景，却没有覆盖真实用户的表达方式。我从评测输入的偏差入手，把“可用”的标准落到业务实体和流程上。

业务位置
  1. 描述需求
  2. 补齐与确认
  3. 生成与评测
  4. 发布使用

我的工作场景与评测集建设、失败案例归因、场景补齐与需求确认方案，并参与生成架构的工程协同。

原有假设

表单、看板、审批、CRM 四类场景跑通，意味着已经覆盖主要需求。

PM 写的测试输入完整，用户却只说“做个客户跟进”。缺少字段与流转规则，生成结果仍然不可用。

用需求补全对照定位问题，统一 UI 与功能评测标准，再把补齐和确认做成产品机制。

场景覆盖，不等于表达覆盖

最初评测验证的是完整需求下的生成能力。内测暴露真实输入缺少字段和流程，因此扩充测试集，并把业务功能完整性纳入标准。

补全需求的对照为输入层改进提供支持，但不能据此断言所有失败都与生成模型无关。场景补全也可能猜错，因此需要用户确认与微调。

机制与工程，共同影响结果

项目还推进了 Todo List 拆解与子 Agent 生成。质量和成本结果来自多项改进，不全部归因于需求确认这一处交互。

回看：让测试更接近真实用户表达，并持续检查补齐错误与确认负担。讲述中“提升 30%”的指标定义不一致，未作为本页结果引用。
